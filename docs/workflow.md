# Как работать с проектом

## Для владельца
Открой проект и опиши желаемый результат обычным языком. Не нужно каждый раз
прикладывать документацию: точка входа для агента — AGENTS.md.

Полезный формат задания: что изменить, где, что сохранить и как понять, что готово.
Например: «Приведи Process к общей типографике. Сохрани текст и порядок этапов.
Проверь в 2560×1440. Другие секции не переделывай».

Для большой работы: «Возьми задачу B01 из backlog, создай план и реализуй».
Для продолжения: «Продолжи активный план; сначала проверь его состояние и рабочее дерево».
Если active пуст, назови новую задачу — рекомендации не запускаются сами.

Обычно выбирай Sol. Для архитектурного выбора или целостного ревью — Astra;
для механических преобразований с готовым правилом — Luna.
Подробности: [routing](../.agents/routing.md). Если переключение недоступно,
агент не должен притворяться, что оно произошло.

Для сбора контекста доступен [локальный Qwen](../.agents/qwen.md).
Можно написать: «Используй Qwen для разведки, решение и реализацию оставь Sol».
Основной агент также может использовать его по разрешённым узким правилам harness.
Вручную: pwsh -NoProfile -File scripts/qwen-worker.ps1 -Task 'Ваш узкий вопрос'.

## Цикл работы агента
1. Прочитать AGENTS.md, проверить git status и документы нужной области.
2. Определить минимальные файлы, результат и область влияния на защищённые системы.
3. Для сложной работы составить ExecPlan по [PLANS.md](../PLANS.md) и добавить
   ссылку в [active](plans/active.md). Простая правка обходится без плана.
4. Внести изменения в разрешённой области, сохраняя незавершённую работу пользователя.
5. Выполнить проверки ниже и обновить только изменившиеся знания.
6. В итоговом сообщении назвать результат, проверки, ограничения и оставшиеся задачи.
   Завершённый план убрать из active и добавить в [completed](plans/completed.md).

## Проверки по области влияния
| Изменение | Минимальная проверка |
| --- | --- |
| Только документация | Ссылки, факты, противоречия, git diff; сборка не нужна |
| TS, компоненты, маршруты | npm.cmd run build и прямой затронутый сценарий |
| Визуальная правка | Браузер в QHD по [responsive](design/responsive.md) |
| Токены / глобальный CSS | Поиск всех потребителей и проверка затронутых секций |
| Events / motion | Cleanup, клиентская граница, ввод и связанные сценарии |
| Кейсы | Карточка → preview → маршрут, правильный slug, неизвестный slug |
| Контакты | href и переход к CTA, без отправки сообщений |

Build не доказывает визуальную исправность. Браузерная проверка не заменяет сборку.
Не добавлять зеркальные тесты для простых обратимых правок; тесты полезны для
выявленного поведения и регрессий. Отдельных lint/test scripts сейчас нет.
Если проверка невозможна, указать точную причину и остаточную неопределённость.

## Обновление знаний
Текущее устройство — ARCHITECTURE.md; требования — профильный документ;
причина существенного решения — ADR в docs/decisions; временный ход работы — план.
Не обновлять все документы после каждого CSS-изменения.
При расхождении с реализацией различать баг, устаревшее описание и новое требование.

## Рабочее дерево и уборка
Перед правками фиксировать исходный git status. Не перезаписывать чужую работу,
не создавать коммиты и не публиковать результат без задачи на это.
Временные скрипты/скриншоты складывать в очевидную временную папку и убирать
после проверки. Сохранять исходные файлы, ассеты, lockfile, node_modules, .next и логи,
если их очистка не запрошена. Проверить итоговый список созданных/изменённых файлов.
